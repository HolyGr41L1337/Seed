# 架构说明

这份文档解释 Seed 的各个部分怎么配合，以及几个关键设计为什么这样做。

## 总览

```
浏览器（web/）  ──HTTP + SSE──┐
其他程序（REST / OpenAI 兼容）─┤
                              ▼
                        src/server/        HTTP、鉴权、REST API、事件流
                              │
                        src/app.js         组装：配置、存储、工具、扩展、运行
                              │
            ┌─────────────────┼──────────────────┐
            ▼                 ▼                  ▼
      src/agent/        src/extensions/     src/providers/
      智能体循环          扩展宿主             模型接口适配
            │
      src/tools/        内置工具
```

一个进程，一个端口。界面只是 API 的一个客户端：界面能做的事，别的程序用同一套接口都能做，AI 自己也通过 `seed_api` 工具走同一套接口。

## 一条消息的经过

1. 客户端 `POST /api/conversations/:id/messages`。服务端把用户消息写入对话，启动一次**运行**（run），立即返回。
2. `src/agent/agent.js` 的循环把对话发给模型，边收边通过事件总线广播增量（`delta`）。
3. 模型要调用工具时：先按 JSON Schema 校验参数，再过审批策略（`src/agent/permissions.js`）。需要询问就广播 `approval.requested` 并等待；否则直接执行，把结果作为下一条消息追加，回到第 2 步。
4. 模型不再调用工具时，运行结束，广播 `run.completed`。

所有事件都带一个全局递增的 `seq`。客户端先连事件流，再取对话快照（快照里也有 `seq`），只应用更大的事件，这样刷新页面或中途加入都不会丢、不会重。

每个对话同一时间只有一个运行。取消通过 `AbortController` 传到模型请求和正在执行的命令（整个进程组会被结束）。

## 统一的消息格式

对话以一种与服务商无关的格式保存（见 `src/agent/messages.js`）：消息有 `user`、`assistant`、`notice` 三种角色，内容是一组块（`text`、`thinking`、`tool_use`、`tool_result`、`image`）。`notice` 是软件给用户看的提示，永远不会发给模型。

每个适配器负责双向转换：

- `providers/openai.js`：Chat Completions 协议。处理各家的差异，例如工具调用分片不带 `index`、`reasoning_content` 是否需要回传（出错时自动切换并记住）、用量字段的不同写法。
- `providers/anthropic.js`：官方 SDK。助手消息除了统一格式，还原样保存 API 返回的内容数组（`meta.raw`），下次原封不动发回去。

同一个对话可以中途换模型：发给哪一家，就按哪一家的格式转换；别家产生的思考内容不会被发过去。

## 为什么系统提示词和工具列表是"冻结"的

对话创建时，系统提示词和工具定义就固定下来，随对话一起保存，之后的每次请求都逐字节相同，历史消息只追加、不改写。原因有两个：

1. **缓存。** 各家的提示缓存都按前缀匹配，前缀里任何一个字节变了，后面全部作废。固定前缀能让长任务的大部分输入按缓存价计费。
2. **Claude 的思考块。** 新的 Claude 模型会校验思考块所属的对话：系统提示词、工具集合或更早的消息只要被改动，之后重放的思考块就会失效。只追加的历史天然满足这个要求。

这带来一个问题：AI 在对话中途给自己加了新工具怎么办？答案是 `ext_call`。它是一个从一开始就在工具列表里的"转接"工具，可以按名字调用任何后来注册的工具。新开的对话则会把新工具作为普通工具直接带上。

万一历史还是对不上（例如软件升级后继续旧对话），官方接口下会请求 API 丢弃失效的思考块而不是报错，并在本地清掉它们，之后的请求恢复正常。

## 上下文整理

每次模型返回后记录本次请求占用的 token 数。超过预算（默认是上下文长度的 75%，上限 20 万）时，在下一次请求前让模型写一份摘要，之后的请求从"摘要 + 摘要之后的消息"开始，摘要之前的内容不再发送。完整记录仍然保存在对话文件里，界面照常显示。

摘要请求沿用对话本身的系统提示词、工具和历史，所以能命中缓存。如果对话已经长到连摘要请求都放不下，就改为对截短的纯文本记录做摘要。

## 审批策略

`permissions.js` 是纯函数：输入模式、工具调用的描述、本对话已有的授权，输出"放行"或"询问"。工具用 `kind` 声明自己的性质（`read`、`write`、`exec`、`network`、`app`），文件类工具还会给出路径。路径按真实位置判断（解析符号链接），分成工作目录内、工作目录外、扩展目录三种情况。

扩展目录单独成类，是因为扩展代码会在服务进程和页面里以完整权限运行。如果把它当普通文件修改，`auto-edit` 模式就等于允许任意代码执行。

AI 通过 `seed_api` 调用接口时带着"来自智能体"的身份：不能改审批模式和服务设置，不能替用户回答审批，不能操作自己所在的对话；它发起的子对话沿用它自己的审批模式，并且遇到需要询问的操作一律拒绝。

## 扩展

扩展是 `~/.seed/extensions/<名字>/` 下的文件夹，可以有 `server.js`（在服务进程里运行）和 `client.js`（在页面里运行），各自导出一个 `activate` 函数。

- **作用域。** `activate` 拿到的对象（服务端是 `ctx`，页面里是 `seed`）是专属于这个扩展的。通过它注册的一切（工具、路由、钩子、界面挂载、命令、定时器）都记在这个扩展名下，重载或停用时全部撤销。所以热重载不会留下重复的东西。
- **新鲜的代码。** 每次重载代数加一。服务端用 `server.js?g=<代数>` 导入，并通过模块解析钩子把这个参数传给它相对导入的文件；页面端从 `/extensions/<代数>/<名字>/` 加载，相对导入自然落在新路径上。两边都不会拿到缓存的旧模块。
- **错误回传。** 这是"让 AI 自己加功能"能成立的关键。服务端激活失败时记录带文件和行号的报错；界面代码先在服务端做一次语法检查（浏览器报语法错误时不给位置）；页面加载完会把每个扩展的结果报回来，运行期抛出的错误也按调用栈归到对应的扩展。`reload_extensions` 工具把这些汇总成一份报告交给模型。
- **隔离。** 一个扩展失败不影响其他扩展；钩子里抛出的错误被记录后跳过。界面被弄坏时可以用安全模式打开。

## 安全模型

- 默认只监听回环地址。所有接口都要访问令牌：程序用 `Authorization: Bearer`，页面用登录后得到的 HttpOnly、SameSite=Strict 的会话 Cookie。带 Cookie 的请求还必须来自 Seed 自己的页面（检查 `Sec-Fetch-Site` 或 `Origin`），因为 Cookie 不区分端口，本机另一个端口上的网页不应该能借用它。
- 只有令牌请求会得到 CORS 许可，Cookie 请求不会。
- 页面被嵌在别的网站的框架里时（IDE、云端的"预览"面板都是这样），浏览器不会保存或发送这个 Cookie。这时页面改为在当前标签页里保留令牌，每个请求用 `Authorization` 头发送；事件流也因此用 `fetch` 读取，而不是 `EventSource`。
- 扩展的界面文件通过 `<script>`、`<link>` 加载，带不了请求头，所以它们的地址里含有一个由令牌派生的密钥（`/extensions/<代数>~<密钥>/…`）。页面从需要鉴权的清单接口拿到这个地址。
- 配置文件权限 600；接口从不返回 Key；文件工具拒绝读写配置文件。
- 模型输出、工具结果、网页内容都按不可信数据处理：系统提示词里明确它们不是指令，界面用 DOM 节点而不是 HTML 字符串渲染。
- 没有系统级沙箱，这一点在 README 里写明了。

## 数据

```
~/.seed/
  config.json            设置、服务商、访问令牌
  conversations/         每个对话一个 JSON 文件，外加列表索引
  toolsets/              按内容哈希保存的工具定义快照，多个对话共用
  extensions/            扩展
  extension-data/        每个扩展的键值存储
```

用 `SEED_HOME` 环境变量或 `--home` 可以换位置。
